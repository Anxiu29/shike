# 服务端代码阅读路线

服务端负责保护模型调用和校验外部数据。餐食记录保存在浏览器IndexedDB；这里的访问码令牌与OSS额度对象并不是餐食云账号或同步数据库。阅读时建议先沿一条完整调用链走通，再看不同供应商的协议差异。

## 从启动到一次识别

1. `packages/server/src/index.ts` 是进程入口：`loadConfig → buildApp → listen`。`app.ts`只装配实例，测试因此可以通过`inject`请求它，不占用真实端口。
2. `config.ts`把字符串环境变量变成受约束配置。测试传入字面量配置时不会读取开发机真实环境文件。原始配置包含密钥，不能打印整个对象。公网模式必须同时具备访问保护与OSS日配额。
3. `app.ts`的`onRequest`先处理来源、Bearer令牌和分钟限频。来源校验不能代替身份验证；原生App可能没有`Origin`。`trustProxy:false`意味着IP来自直接连接，部署到代理后需理解真实IP与本地限频口径。
4. `/api/recognitions`先验证multipart字段和上传体积，取得并发槽位，再由`image.ts`验证真实格式、像素数、单帧和解码结果。图片会应用相机方向、缩小、铺白底并重编码为JPEG，原始EXIF/GPS不会传给模型。
5. 清洗成功后，`limiter.consumeDaily`与可选的`quota.consume`预留一次调用，随后调用模型适配器。无效图片不会扣日额度。限频、并发和日额度是三个不同边界，不能互相替代。
6. `vision/index.ts`决定供应商实现，`vision/http.ts`负责出站HTTP，再由适配器提取文本、`vision/parse.ts`映射共享验证错误。HTTP200、合法JSON和合法识别结果是三个不同层次。
7. 路由用`finally`释放槽位，`app.ts`的统一错误处理器只公开稳定错误；SDK异常或上游原始正文不能直接返回浏览器。

## 从文字输入到待确认草稿

`/api/meal-assistant`使用共享schema限制文本、最多6条上下文和最多3张图片。它与识别接口共用并发槽位及日额度，避免切换接口绕过资源限制。

`meal-assistant.ts`按顺序清洗本轮和历史图片，全部成功后才调用路由传入的`beforeRequest`扣额回调。顺序处理的原因是：如果并行解码的一个任务先失败，不能让路由释放槽位时还有其它解码任务在后台运行。随后构造供应商请求、提取返回文本并验证草稿。结果仍需用户确认，助手不会直接写入餐食。

读`try { return await ... } finally { release(); }`时特别留意`await`：直接返回Promise会让`finally`提前执行，模型未完成就释放槽位。释放函数本身是幂等的，重复调用也不会把活动数减为负数。

## 超时、流与错误

`http-body.ts`集中管理响应读取：累计实际字节数，在上限内才保留块，读完后一次解码UTF-8，以免中文字符被分块切断。`Content-Length`可能缺失或不可靠，不能代替实际计数。

`Promise.race`只让调用方停止等待，不能自动结束底层操作。因此模型HTTP层同时使用AbortController，读取器也监听信号取消流。取消是资源清理，可能失败甚至永不结束；`discardResponse`和读取异常路径触发取消但不等待取消完成，确保业务错误能及时返回。`finally`移除监听器并释放reader锁。

这次审查将Gitee更新接口原先的手写读取改为该共享读取器：HTTP错误或正文超限时，永不结束的取消操作不会继续占用更新并发槽；正文下载在截止信号触发后也会停止。更新接口只代理固定公开JSON地址，每次重定向都重新校验主机，模型认证头不会参与更新请求。

## 日额度为什么要用原子追加

`quota.ts`一天对应一个OSS追加对象，一次预留追加一个字节，长度就是次数。读取长度为n后以`position=n`追加，相当于比较并写入：多个实例看到同一个n时只有一个成功，冲突者重新读取。只有明确的位置竞争才最多重试4次，网络写入结果不明时不能盲目重试。

`OssDailyQuota.consume`最长等待8秒。超时信号会阻止迟到的长度读取继续发起新的追加或竞争重试。这次新增的回归测试证明：超时返回后才完成的读取不会再扣一次额度。

仍需理解保守计费语义：已发送的OSS追加或模型请求可能在本地超时后成功，系统不能断言供应商没有计费，也不自动退回已预留次数。内存计数和OSS预留不是跨系统事务，OSS不可用时，本进程已计入的尝试不会回滚；这会偏向少用额度，而不会绕过成本上限。分钟窗口与并发仍为单进程状态，多副本部署不能把它们当作全局保护。

## 令牌与其它入口

`auth.ts`用访问码换取7天HMAC签名令牌，payload仅有版本、到期时间和随机nonce。base64url只是编码，payload不能放密钥。先限制令牌字符和长度，再验签、再解析。轮换访问码或签名密钥会让旧令牌失效。

`food-catalog.ts`只读固定条码来源。`null`代表来源明确报告没有该商品；网络或解析失败要报错，不能伪装成未找到。`app-updates.ts`只代理公开版本列表或更新JSON，不代理APK。两者的查询限频独立于模型调用额度。

## 本地验证与验证边界

在项目根目录执行`npx vitest run packages/server/src`可运行服务端测试；`npm run typecheck -w @shike/server`只做服务端类型检查。测试通过不代表真实模型、真实OSS权限、代理配置或所有外部数据内容都已验证。

本轮新增4个回归用例，先观察修复前失败，再实施最小修复：两种取消操作永不完成的更新错误路径、更新正文下载中止、OSS额度读取超时后禁止迟到扣额。认证、跨实例竞争、北京时间午夜切换、坏图不扣额、异常后释放并发槽位等现有测试继续保留。
