# 网页数据链路学习笔记

这份笔记按“用户操作 → 草稿 → 外部边界 → 数据库”的顺序解释网页数据层。对应的中文注释放在关键函数旁边，适合一边断点一边阅读。备份文件版本、数据库版本和应用版本是三个不同概念，不能互相替代。

## 先读这六处

1. `packages/web/src/components/FoodEditor.vue`：一餐的内存草稿和图片处理状态。
2. `packages/web/src/lib/image.ts`：原图检查、压缩、资源释放。
3. `packages/web/src/lib/api.ts` 与 `connection.ts`：请求路由、响应验证、超时和会话。
4. `packages/web/src/lib/db.ts`：校验、快照、原子提交。
5. `packages/web/src/views/SettingsView.vue`：备份预览与显式恢复。
6. `packages/web/src/lib/backup-file.ts`：浏览器下载或安卓系统分享。

## 一餐为什么有“草稿”和“已保存快照”

编辑器初始化时会深拷贝已有条目。直接把父组件的记录当草稿修改，会使用户点取消后仍看到已改变的数据；独立草稿避免了这个问题。每项食物保存营养与来源快照，因此后来修改食品库不会倒推改写旧餐。

照片识别经过 `processFile → runRecognition → prepareRecognition/prepareOfflineImage`。压缩与模型请求都成功后，转换函数产生待核对条目，组件才替换清单。识别失败时不把旧清单清空，也不把失败当成空餐保存。模型返回只是建议，记录仍需用户核对。

`phase` 描述照片的压缩、识别、完成或失败；`saveBusy` 描述提交后的存储等待。两者独立，识别完成也可能尚未保存。提交时再次克隆条目并做 schema 校验，再 `emit('save', record, photos)`。事件只把控制权交给父组件，不能把它当成已经完成的数据库写入。

保存期间，原生 `fieldset[disabled]` 冻结编辑区的输入与按钮。否则用户可能在事务已拿到旧快照后删掉某项，界面显示新清单，数据库却保存旧清单。父组件成功后关闭编辑器；失败通过 `saveFailed(message)` 解锁原草稿，用户可以继续修改和重试。

滚动容器仍是外层 `div.editor-scroll`，内层 `fieldset.editor-fields` 只负责分组和禁用。`fieldset` 有浏览器内部内容盒，直接让它承担 flex 滚动布局时，桌面长配方可能溢出并挡住保存按钮；不能用强制点击绕过这种真实交互问题。`meal-assistant.spec.ts` 的常用配方再次加入流程覆盖了普通点击保存，`data-consistency.spec.ts` 继续验证原生禁用继承。

## 图片为什么要先压缩

原图先检查 MIME 和 20 MB 文件边界，再交浏览器解码。有效 MIME 不代表文件真的能解码，因此解码仍有独立的错误提示。解码后检查像素规模，再用 Canvas 输出最长边不超过 1280 的 JPEG。画布重编码仅保留像素，不复制原始 EXIF/GPS 元数据；透明区域先铺白，避免变成黑色背景。

每轮编码等待 `toBlob` 完成，最多五轮降低尺寸和质量，目标是二进制不超过 1 MB。同一个压缩结果用于模型请求与本地照片；Base64 额外增加约三分之一体积，所以不能把它看成免费的字符串转换。

位图必须在 `finally` 中 `close()`，预览 Blob URL 在换图或卸载时释放。文件字节数和解码后的像素数限制有不同作用：像素检查发生在解码之后，因此不保证低内存设备解码时一定不会内存不足。大图和不同 WebView 仍需真机验证。

## 请求为什么捕获一次连接配置

服务地址只允许 HTTPS origin，不带路径、账号、查询和片段。开发网页可用同源 `/api/`；独立安卓 App 没有本地 Node 服务，不能把自己的 `https://localhost` 当成识别后端。

网络入口先决定本机离线、手机直连或自建服务，再发请求。用户选择本机方式时，失败不会自动把文字和照片转发到在线服务。自建服务请求在开始时捕获地址与令牌，保证同一次请求不会在中途换服务后串用凭证。

识图和文字助手收到 401 时，只清除这次请求实际使用、并且当前仍匹配的令牌，保留服务地址。例如：请求 A 使用旧令牌发出，用户随后重新连接得到新令牌，A 的 401 晚到时不能删掉新令牌。`connection.test.ts` 包含这个竞态场景。

`fetch()` 成功返回只代表响应头到达，响应体的 `json()` 仍可能等待很久。超时控制器必须覆盖整个下载与解析阶段。`servicePayload` 只把 JSON 语法错误降级成 `null`，保留中断和网络异常；外层再按各入口转换成超时或网络提示。把所有解析异常都 `catch(() => null)` 会把真实超时误报成“草稿无效”或“凭证无效”。

请求最终结果还必须通过共享 schema。HTTP 200 只代表服务端声明请求成功，不能证明营养字段或草稿结构有效。健康检查同样只证明当前配置和可达性，不能证明真实模型调用一定成功。

## IndexedDB 事务保护哪些东西

`saveMeal` 先克隆为普通 JSON 并校验，避免 Vue Proxy 无法结构化克隆，也避免无效字段写入数据库。它在同一事务里保存餐食、照片、个人估算和每日预算。任一步失败都回滚，不能出现餐食没保存、个人估算却已经更新的半成功状态。

照片参数有三个含义：`undefined` 保留原照片、`[]` 明确删除、非空数组整组替换。编辑器异步读到的旧照片只用于预览，不能顺手把它当成“用户修改后的照片”回填，否则普通改餐也会重写照片。

事务里只等待数据库操作。图片压缩、网络请求和系统分享应放在事务外，避免长时间占用写锁或在 IndexedDB 已自动结束事务后继续写入。只有事务 Promise 成功完成，界面才可以显示保存或恢复成功。

`loadData` 和 `exportBackup` 使用同一个只读事务读相关表；否则多标签页或恢复操作可能让结果一部分来自旧数据、一部分来自新数据。只读事务同样具有一致性价值。

## 恢复为什么先预览再整体替换

设置页先检查文件大小，再读取文本并由 `parseBackup` 验证、升级到当前备份格式。这里只生成 `pending` 预览，不写数据库。用户确认后，`restoreBackup` 才在一个读写事务里清空并恢复所有业务表。

旧版本缺少的表经升级会补成空数组。因此恢复旧备份也是整体替换，可能清空本机后来增加的照片或收藏，界面明确提示先导出当前备份。这是当前产品定义，不是增量合并。

文件上限按 UTF-8 字节数计算，不能只用 JavaScript 字符串长度代表文件大小。导出可跳过读取照片来减少内存，但当前 JSON 格式仍一次生成完整对象和字符串；100 MB 是文件上限，不是峰值内存上限。特别大的备份应在真实手机测量，不能仅凭桌面测试判断。

Web 分配一个临时 Blob URL 触发下载，稍后释放。安卓先写 App 缓存，再把 URI 交系统分享菜单。系统分享流程返回并不证明用户已经把备份存到持久位置，缓存也可能被系统清理，用户仍需要另存。

## 用测试理解边界

`connection.test.ts` 用可控网络边界模拟响应头已到、响应体一直等待，推进定时器触发超时；它验证实际错误分类而非只验证定时器存在。`FoodEditor.test.ts` 覆盖提交后冻结与存储失败后解锁。happy-dom 尚不计算 fieldset 的禁用继承，测试按该表单没有 legend 的原生规则辅助判断；实际点击行为和滚动布局由浏览器验证。

`storage.test.ts`、`meal-photos.test.ts` 和 `food-library.test.ts` 使用 fake IndexedDB 验证回滚、快照独立性、照片保留/替换和库保存；`backup-file.test.ts` 验证交给安卓文件与分享接口的边界。这些测试不能证明真实设备存储配额、真实网络延迟、系统分享结果或模型营养估算准确性。
