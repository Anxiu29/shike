# 手机离线 AI：文字记餐与测试

当前Android 0.11.24-test沿用下述0.11.23的离线记餐与模型文件，拍照另改为[系统相机](system-camera.md)以移除CAMERA权限；不需要重下模型。以下版本说明聚焦离线AI的变更与验收。

当前0.11.23-test（versionCode46）修复本机记餐的单位校验。0.11.22-test把Qwen2.5-1.5B接入首页文字记餐，用户Find X9回传流程正常，但“2个／1碗／1杯”全部显示“2g／1g／1g”，数量未变。此反馈表明JSON格式约束不能保证计量语义正确；未采集原始模型JSON，单位问题按用户现象复现。报告在 `artifacts/android/offline-meals-find-x9-user-report.json`。

新版在接收模型草稿后，以紧邻原文食物名的明确数量和单位核对，两/半/小数及标准千克、升换算可解析；不靠常见重量反推单位。未改动的食物保留上一草稿数量与单位。没有数量保持未知，歧义、未支持的瓶/盒等单位、无法定位食物名的数量修改会报错并保留输入和草稿，请重写明确描述或详细编辑。该规则有意保守，不覆盖所有中文表达，也不修改已保存的历史记录。参考克重仍由本地规则估算并单独标示，最终需用户核对。

0.11.23验证：545项单元/接口测试、构建及类型检查通过，24项Android JVM策略检查通过。最终APK解包资源在禁外网及模拟桥下通过6项Chrome手机/Edge桌面场景，故意返回2g/1g/1g，验证原文恢复个/碗/杯、继续修改、确认保存与刷新，以及错误/取消保留草稿和图片拒绝。15项页面资源与构建逐字节一致；同签名升级及下载完整SHA核验通过。报告在 `artifacts/android/offline-unit-verification.json`。用户随后回复“没问题了，继续”，确认本次单位修复复测通过；这是用户反馈，未采集原生推理日志或新增性能数据。

## 离线文字记餐

1. 先导出记录备份，再覆盖安装新版，勿卸载。已有模型位于相同的应用私有目录，升级不需要重新下载。
2. 设置 → 手机离线 AI：没有模型时下载或导入；已有模型可点“用于文字记餐”。回首页打开“AI记餐”，选择“本机离线”，再手动点击“准备模型”。打开助手、选择离线或切换CPU/GPU都不会自动加载，不下载、不使用Key。
3. 保持GPU选项（旧版已在用户Find X9上跑通），必要时可手动选CPU。输入“午餐吃了两个鸡蛋、一碗米饭和一杯牛奶”。模型生成JSON，应用校验后显示草稿；核对日期、餐次、食物、数量和参考份量，再“确认保存”或“详细编辑”。模型不计算热量，营养来自已有本地食品库；未知营养保持待补充。
4. 可继续输入“鸡蛋改成一个，去掉牛奶”。每次返回完整新草稿；问答不修改旧草稿；“取消这餐”仅清空未保存草稿。自然语言复述、截断JSON、错误单位、超限数量、日期餐次不符等会报错，输入和旧草稿保留。
5. 本机模式只处理文字，不上传描述或图片到在线模型。当前/历史图片不能静默丢弃，需新建纯文字对话或手动切在线模型。主页面拍照继续使用原有独立模型配置，离线文字选择不会替换拍照模型。没有自动云端回退。

本机每次最多600字，参考当前完整草稿及最近一轮文字对话。运行引擎在应用前台复用，关闭助手不立即释放；连续5分钟未调用或App退后台后释放。释放后或更换CPU/GPU，需要再次手动点击“准备模型”；未准备时发送只提示并保留输入和草稿。JS检查状态后，原生发送入口也再次检查已准备引擎，不自动重新加载。正在加载/整理时可关闭助手来请求停止；生成时也可点“停止”。取消不保存、不替换已有草稿。下载和导入、已有模型名/哈希均不变。

新版使用4K总上下文、最多768输出token及LiteRT-LM的JSON Schema约束。受约束JSON只保证格式的一部分；Zod、本地日期/餐次与意图规则再校验，最终仍需人核对食物和份量。常见份量由既有本地规则填入并标“份量估算”，不把模型未给出的克数当作实测。相比旧版19字符复述，完整JSON更长且需要准备格式约束，实际耗时、成功率和修改能力需用户手机复测。

0.11.22验证：最终完整510项单元/接口测试通过，24项Android JVM策略测试通过；15项Chrome手机源码场景通过，最终APK解包资源在禁外网及模拟原生桥下28项Chrome手机/Edge桌面场景通过，另2项仅适用于H5后端的演示场景跳过。覆盖无Key离线草稿、修改/移除、核对保存与刷新恢复、失败及取消保留旧草稿、问答与清空边界、图片拒绝、在线图片记餐回归和窄屏操作。15项包内页面资源与构建产物逐字节一致，新增记餐方法/原生库编入DEX/APK；versionCode45及同签名升级核验通过，局域网下载的完整APK哈希与构建一致。报告在 `artifacts/android/offline-meals-verification.json`。这些检查不代替0.11.22在用户Find X9上的JSON约束、耗时和语义准确率验收，旧0.11.21只验证过自由文字生成。

## 保留的独立测试入口

1. 先导出记录备份，再覆盖安装新版 APK，勿卸载旧版。
2. 设置 → 手机离线 AI → 下载模型。约1.60GB，建议Wi-Fi并保持前台直至完成；停止或网络中断后支持续传。App切后台不主动取消下载，但系统可能回收进程，已落盘部分可继续下载。完整性校验也需要时间。
3. 下载站无法访问时，点“下载失败或想手动导入？”中的指定文件链接，用浏览器下载，再“从文件导入”。也可从电脑传入该文件；选择文件通过系统选择器，无需开放全盘存储权限。导入会复制一份，需额外留出约 1.6GB。
4. 选 GPU，点“加载模型”。失败后手动选 CPU 再加载，不自动更换计算方式或调用云端。
5. 可开启飞行模式，点击“生成回答”，观察首段等待与生成总耗时；第二次生成复用已加载的引擎，但每次是独立问题，不带聊天历史。
6. “复制测试数据”仅复制设备、引擎、耗时、字符数及状态，不包含问题、回答或记录。对比GPU与CPU前先“释放内存”。未启用离线记餐时，关闭测试页释放模型；启用后按上述前台复用规则处理。App切后台停止生成并释放引擎，初始化过程中需等待加载返回再释放。

输出最多256 token，可能在长度限制处结束；120秒仍未结束会请求停止。输出字符数不等于token数。首段等待是原生回调收到第一段非空可见文字的时间，不含模型加载；总耗时包含问题处理与生成。界面每500ms读取一次原生快照，显示的“系统当前可用内存”不是模型峰值内存。实际速度、发热及识别质量必须在真机确认。

## 固定模型与来源

- 模型：`litert-community/Qwen2.5-1.5B-Instruct`，Q8、4096 KV版本 `.litertlm`。0.11.21测试限制2048 token；0.11.22记餐使用4096 token，无图像、音频或NPU执行器。
- 文件：`Qwen2.5-1.5B-Instruct_multi-prefill-seq_q8_ekv4096.litertlm`
- 大小：`1597922856` 字节（十进制1.598GB，约1.488GiB）。
- 固定仓库版本：`2f23bacf8ec78b83dfcd7271c5cb25777b1be5e0`
- SHA-256：`c4a9b7289365ab80fe599b844b77ad253eb3c53fb0e5d963d699146a6f01255e`
- [模型卡与Apache-2.0许可](https://huggingface.co/litert-community/Qwen2.5-1.5B-Instruct)；大小与SHA来自该版本的Hugging Face LFS元数据，2026-10-27核对。
- 推理引擎固定为[Google LiteRT-LM Android 0.18.1](https://developers.google.com/edge/litert-lm/android)，通过Java互操作调用Kotlin API。引擎和模型皆为Apache-2.0；模型不嵌入APK，下载/导入后位于应用私有的noBackupFilesDir，不进入记录备份或安卓自动备份。

下载只接受固定URL及HTTPS的Hugging Face官方域名跳转。续传检查Content-Range，大小及SHA均通过才把临时文件提交为模型。导入也只接受该指定文件，不执行未知模型。已验证的旧模型不会因导入失败被覆盖；删除模型需要明确点选确认。

## 实现与验证边界

`OfflineAiPlugin.java`负责后台文件流、校验、引擎生命周期、取消和原生计时；`OfflineModelPolicy.java`负责来源、大小、哈希限制；`offline-ai.ts`与`OfflineAiTest.vue`负责状态轮询和测试界面。只进入首页或设置不加载模型、不下载、不推理。Android 8.0以上ARM64独立APK开放入口；旧系统给出提示。

构建、JVM策略测试、网页模拟桥测试只能确认代码和交互契约，不能替代Find X9真机运行。尚未在用户手机验证前，不将官方其他手机的tok/s数据作为本机测试结果，也不将文字测试视为离线拍照识别已经完成。

用户随后回传的真机结果：OPPO PLJ110（用户此前说明为Find X9），LiteRT-LM0.18.1、Qwen2.5-1.5B Q8、GPU路径生成完成；加载65.63秒、首段等待1.03秒、生成总耗时1.78秒、输出19字符、系统当时可用内存3.45GB。原始指标记录在 `artifacts/android/offline-ai-find-x9-user-report.json`。这是用户报告，未通过USB直接采集；是否首次加载、是否飞行模式、具体输入/回答和二次加载时间尚未提供。可确认一次文字生成路径跑通，不能据此确认长期稳定性、答案质量、token/s或模型峰值内存。65.63秒计时不含下载与哈希校验；缓存目录已配置，但缓存是否明显改善该机二次加载仍需对比。

后续用户再次回传：同设备、模型、GPU，加载5.29秒、首段等待1.01秒、生成总耗时1.81秒、输出19字符、系统可用内存3.07GB。记录在 `artifacts/android/offline-ai-find-x9-reload-report.json`。加载比前次减少60.34秒（约91.9%），说明65.63秒并非每次固定加载成本，符合首次准备和缓存改善的表现；目前没有原生性能日志，不能区分GPU编译缓存、系统文件缓存和其他状态各自的贡献。两次短回答的响应时间接近；尚未收到具体问题与回答，未确认答案正确性或长文本性能。

用户随后补充了该样例的输入/回答：要求把“午餐吃了两个鸡蛋、一碗米饭和一杯牛奶”整理成仅名称与明确数量的清单，模型返回“午餐吃了两个鸡蛋，一碗米饭，一杯牛奶。”，共19字符，与指标一致。人工核对：三种食物及数量均保留，未额外编造重量或热量；但输出仍为原句复述，未遵守清单格式和只列名称/数量的要求。此样例仅支持内容提取正确的有限结论；接入结构化记餐前需要明确输出契约与结果校验。
